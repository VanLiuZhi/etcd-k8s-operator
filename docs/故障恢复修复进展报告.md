# etcd-k8s-operator 故障恢复修复进展报告

## 问题背景

### 原始问题
- 使用方案3代码解决了size状态同步问题，但失去了故障恢复能力
- 当删除1个pod（总共3个）时，无法自动恢复到3个节点
- 原dev-1分支具备故障恢复能力，但方案3破坏了这个功能

### 目标
- 保持方案3的size状态同步优势
- 恢复故障恢复能力
- 当pod数量不足时，控制器能自动创建缺失的pod

### 第四阶段：状态计算问题发现（2025-09-05）

#### 发现CRD状态计算错误
**问题描述**：
- 当有Pod处于Failed状态时，CRD的`size`字段计算错误
- 实际：2个Running + 1个Failed = size: 3（错误）
- 正确：应该只计算健康的Pod，size: 2

**问题代码**：
```go
// 错误的计算方式
status.Size = len(ready) + len(unready) // 包含了Failed状态的Pod
```

#### 修复状态计算
修改了`calculateDesiredStatus`函数：
```go
// 修复后的计算方式
for _, pod := range pods {
    if pod.DeletionTimestamp == nil && metav1.IsControlledBy(pod, cluster) {
        if k8s.IsPodReady(pod) {
            ready = append(ready, pod.Name)
        } else if pod.Status.Phase == corev1.PodFailed {
            // Failed状态的Pod不计入size
            failed = append(failed, pod.Name)
        } else {
            unready = append(unready, pod.Name)
        }
    }
}
status.Size = len(ready) + len(unready) // 只计算健康Pod
```

- Cluster实例尝试添加第3个成员时遇到etcd quorum问题

### 技术障碍
1. **etcd集群quorum要求**：2个节点的etcd集群无法达成quorum来添加新成员
2. **成员管理复杂性**：Cluster实例卡在成员清理循环中
3. **状态同步与资源管理的协调**：方案3分离了这两个职责，但协调不够完善

## 关键发现

### 架构问题
1. **职责分离不当**：方案3将状态管理移到Reconciler，但资源管理协调不够完善
2. **直接Pod创建的错误**：Reconciler不应该绕过etcd集群机制直接创建Pod
3. **状态计算不准确**：Failed状态的Pod被错误计入集群size

### etcd集群特性
1. **quorum要求**：etcd集群需要多数节点健康才能进行成员变更
2. **成员管理复杂性**：etcd成员的添加和移除需要精确的协调
3. **状态同步延迟**：Pod状态与etcd成员状态之间存在同步延迟
